# Future work

v1 ships local tasks, Daily/Weekly/Monthly Review, weather, Quick Links, and three window modes (Sidebar, Floating with Expanded/Orb, Desktop).

This file is a roadmap and idea list, not a specification. Nothing here is promised, and nothing here is implemented until it ships. Directions carry a light status: **Planned** (intended next), **Exploring** (shaping up, not committed), **Ongoing** (standing policy).

## Directions

### Application lifecycle management — In progress (v1.2.0)

Goal: introduce installation maintenance, including authenticated updates, recovery, installation receipts, Windows Installed apps integration, and uninstall with local data retained by default.

**Phase 1 is implemented** (manual trusted bootstrap with v1.1 adoption, the installation receipt, launch admission, Windows Installed apps registration, Start Menu reconciliation, interrupted-install recovery, and native uninstall keeping local data by default — see [Application Lifecycle & Maintenance Architecture](docs/application-lifecycle.md) for the recorded semantics and deviations). The main app's Settings expose the managed uninstall entry, which hands off to the same native helper that Windows Installed apps uses.

**Phase 2 — the signed updater — has its verification core implemented** (commit `df75c83`), **its provider discovery layer implemented** (commit `eace586`), **its trusted-target/package-staging half implemented** (commit `c8a37ab`), **its frozen-`UpdateSession` + authenticated-helper-handoff layer implemented** (commit `27dbd55`), **its runtime-mutation transaction implemented** (commit `c8e7c03`), **and its probation/HealthAck/commit/rollback/recovery completion half implemented** (commit `b825d33`): the core authenticated update transaction engine now exists end to end. The wire-level protocol was frozen as Phase 2A design in the [Maintenance protocol v1](docs/maintenance-protocol-v1.md): the signature covers the exact raw manifest bytes (no reserialization), Ed25519 with a compiled read-only trust store keyed by SHA-256 key ids, bridge-release key rotation, the receipt/session authority boundary, durable session milestones, and version-selection rules. The verification core is a shared pure-Rust crate (`desktop-todo-update-core`) linked by both the product binary and the helper — strict closed signed-envelope/manifest parsing, canonical Base64, exact raw-byte signature verification before parsing, semantic validation, a typed error taxonomy, and the bounded candidate-eligibility planner (candidate-ineligible vs candidate-invalid, bridge reachability) — each binary verifying independently with its own compiled trust store. The discovery layer is a main-application module that runs GitHub/Gitee/Auto bounded candidate enumeration and bounded metadata fetch and feeds the exact served bytes into that shared verifier — provider identity is discovery-only, and an accepted target lives in memory only until durable persistence. Since commit `c8a37ab` the main-application module also owns the durable trusted target — only a verified target can be persisted, raw manifest/envelope bytes are stored under the frozen per-session layout, restart recovery re-authenticates the disk state through the shared verifier (persisted never means trusted), the actual installed source version is rebound on recovery — plus bounded package download with exact size/hash verification and session-bound staging of the two managed executables, gated by a hard whole-scan budget (an implementation transport policy). Since commit `27dbd55`: the frozen `UpdateSession` envelope (schema 1, closed) is published only from a recovered `PackageStaged` session, with every signed-derived field derived from the re-verified target inside the publisher and re-publication after restart failing closed on any disagreement; the `--expected-manifest-sha256` binding has exactly one source — the digest of the verified raw manifest bytes — carried through the frozen helper CLI (`--update --session-id <UUID> --expected-manifest-sha256 <64 hex>`) and checked four ways on the helper (CLI value == session value == recomputed persisted-bytes digest == re-verified target digest); the helper parses only that frozen CLI form and independently re-verifies the session, installation bindings, source-version rebinding, persisted envelope/manifest through the shared core with its own compiled trust store, the staged package through the shared ZIP validator, and every staged executable by fresh hash — stopping at the unforgeable `ValidatedHandoff` boundary (private fields, no public constructor) with the verified digest journaled; session/staging/manifest/target identity bindings and crash-restart revalidation are covered by deterministic tests; and the package ZIP validator lives in the shared maintenance library as the single implementation both binaries call — the main application still owns acquisition and staging, the helper only revalidates, and the helper stays fully offline with no provider, HTTP client, or download responsibility. Since commit `c8e7c03` the runtime transaction itself runs from that boundary: the main application's production spawn boundary launches the canonical installed helper with the exact frozen argv and exposes the durable-handoff wait; the helper binds the live caller identity (PID + creation FILETIME + canonical image, jointly — PID reuse fails the creation-time comparison, an exited or unqueryable caller fails closed), reuses the Phase 1 `Gate` and exclusive application lease with no second lock mechanism, journals the handoff facts before moving the receipt to `Updating` + `activeSessionId` (`currentVersion` stays source-side; no registry `DisplayVersion` write), continues from a verified session runner through the ready-marker ownership handshake, and applies exactly the two managed executables under intent-before-side-effect ordering — durable intent, fresh preimage verification, deterministic frozen backup slot, backup verification, journal of old facts, same-volume replacement, fresh target verification, journal of completion. Crash reconciliation treats journal and filesystem as joint evidence: a landed replacement with a missing completion journal is reconciled by preserving the OLD backup byte-identically and recording only the completion, and a read-only classifier reports the position (`NoActiveUpdate`, `HandoffPrepared`, `UpdatingNoMutation`, `BackupPartial`, `ReplacePartial`, `ReplacedAwaitingLaunch`, `LaunchedAwaitingHealth`, and the 2D-B completion positions, `Inconsistent`). Since commit `b825d33` the completion half is implemented: the health nonce (OS CSPRNG, 32 bytes / 256 bits, canonical form, journaled into the durable session before any launch, environment-transported to the exact child, never logged, and consumed by the durable `acceptedHealth` record as the replay barrier); the suspended-creation probation launch (`CREATE_SUSPENDED` → identity capture → durable `probationProcess` → `ResumeThread`), which structurally removes the launch/admission race — the child's first instruction finds the authoritative session+nonce+process binding already in place; `PostUpdateProbation` admission admitting only that exact child while the receipt is `Updating` (session, nonce, receipt active session, journal session, PID, creation FILETIME, canonical image, and the installed target main binary's fresh-open hash all bound; ordinary launch during `Updating` stays refused and routes the frozen Q14 recovery entrypoint); HealthAck written only by the admitted child after core initialization, validated in the strict frozen wire shape including a live re-check of the journaled process identity; the typed probation decision distinguishing valid ack, child exit, bounded timeout, invalid/replayed marker, and lost process identity (process creation success is never health success; every failure terminates the exact journaled child — never by name — and rolls back); the commit transaction, only after durable `acceptedHealth`: journal `commitIntent` → fresh-verify the target set → integration/registry at the target → installed evidence → receipt `Installed` at the target → session `committed` → bounded cleanup; the rollback transaction: journal the decision → verify the fixed OLD slots → restore both executables → integration/evidence/receipt at the source → session `rolled-back` → cleanup preserving the verified OLD slots, with mixed crash states recovered by independently observing each destination (restoration is sequential, so mixed destination states are real crash windows) and any missing/mismatching rollback asset failing closed; commit and rollback idempotently resumable through the executed `--recover` entry, which also marks `recovery-required` on inconsistency; terminal truth kept separate from cleanup (a cleanup failure after a durable `committed`/`rolled-back` is retryable debt, never a verdict change, never a rollback of a committed update); and the production `install_ready_update(sessionId)` backend wiring — the frontend supplies only the session id, the backend re-derives every authority from canonical state (staged-session recovery, trust-store reverification, source rebinding, canonical helper spawn, the durable-handoff wait, then the canonical app shutdown), and no path, URL, digest, trust fact, file hash, or helper argument can come from the frontend. Since commit `46d911b` the release-signing **infrastructure** is also implemented: the compiled production trust root has a real deterministic provisioning mechanism (`update-core/src/production_keys.rs` — raw public keys only, duplicate/mismatched entries fail closed, one shared source of truth for both binaries with pinned main/helper parity, no provider/frontend/runtime injection), and the offline operator signer `desktop-todo-release-signer` (separate operator tooling, not a runtime component) validates the manifest first, requires the signing key's derived key id to be an exact member of the same compiled production trust store before signing, signs the exact raw manifest bytes, and re-verifies the produced envelope through that same compiled store before publishing output (operator runbook: [release-signing.md](docs/release-signing.md)). The compiled production trust store remains **empty and fail-closed**: production signing refuses every key and no real release can be authenticated yet — infrastructure implemented is not production signing enabled, and no real private key exists. The remaining work is release-facing: the **real production key ceremony** (1. generate the real Ed25519 keypair OUTSIDE the repository, 2. secure the private seed offline, 3. derive the public key and key id, 4. add only the public key to `production_keys.rs`, 5. review + commit the provisioning, 6. rebuild the binaries, 7. sign the release, 8. verify the signer reports the key as provisioned, 9. publish) and the first signed production release; the release publishing pipeline (GitHub/Gitee publishing and mirror publication/readback verification); the frontend updater surface (`check_for_updates`, `download_update`, install/restart UX, and the Settings release-source preference); and the real-Windows RC gates (including the PE ProductVersion positive path). The main app owns discovery, package acquisition, and the install trigger; the small offline native `desktop-todo-maintenance.exe` owns the whole mutation/probation/commit/rollback transaction after its handoff validation — re-verifying every signature and hash itself, exactly as the handoff already does. Signed manifests and both sources are first-release requirements for automatic updates, not optional later additions. v1.2.0 is the planned first self-maintaining release and reaches it only through the manual trusted bootstrap — v1.1 has no updater or trust root, so no automatic path into v1.2.0 exists.

Reaching a formal v1.2.0 release still requires release preparation: the version bump plus verification that `ProductVersion`, `Receipt.currentVersion`, the Installed-apps `DisplayVersion`, and the release version all agree, the exact compiled nine-entry package-allowlist check (including `THIRD_PARTY_NOTICES.md`), and notice/dependency completeness (`cargo audit`, `cargo deny`, `pnpm audit` — not yet executed). The build half of that preparation is implemented: `scripts/build-release-binaries.ps1` builds the two production binaries through the frozen canonical commands and verifies versions, paths, and hashes. Everything downstream of the binaries — flat ZIP assembly, manifest generation, tag/provenance, and publishing to the mirrors — is not implemented. Exact-byte Ed25519 signing of the manifest is implemented as the offline operator signer (commit `46d911b`), but it cannot produce a real release until the production trust store is provisioned through the key ceremony above. The frontend update UX (check-for-updates, download progress, install/restart, Settings release-source preference) is not built. Beta channels, background/resumable downloads and automatic checks remain later work.

### Review export — Planned

Goal: export Review and statistics results.

Likely scope: Markdown first, then CSV and JSON; PDF/image export only after those exist. Export reuses the existing read-only Review computation — the same aggregation, a different sink — and does not re-implement statistics.

### Modular feature architecture — Exploring

Goal: make feature modules more independent and easier to enable, disable, and combine — without building a plugin system.

Likely scope: Today, Weather, Review, Quick Links, News first, then further cards. Each module keeps an explicit data/provider boundary, settings, view/component, and lifecycle.

Not now: no generic plugin API, no dynamic loading, no marketplace.

### News / daily briefing — Exploring

Goal: a card of user-chosen keywords/topics shown in the same surface, each item opening in the default browser. No extra complex window.

Boundary: prefer stable APIs, feeds, or other structured sources over fragile HTML scraping. Implementation is deliberately unspecified until the direction firms up.

### Compatibility and maintainability — Ongoing

- The Windows native layer is frozen-by-default ([CONTRIBUTING.md](CONTRIBUTING.md)): only concrete bugs, OS/dependency compatibility, or a clear product need move it.
- Prefer reducing environment dependencies over adding high-maintenance purely visual native effects.
- Windows 10 compatibility is a possible future validation target, not a promise: it is not claimed as supported before it is actually tested.

## Deferred ideas

No direction yet; recorded so they are not reinvented by accident.

- Hourly and 7-day forecasts, radar, AQI, UV, sunrise/sunset, wind dashboards, severe-weather warnings, and weather notifications
- Windows GPS, IP-based location, weather-driven backgrounds, and AI weather summaries
- Charts, heatmaps, evaluative trends, productivity scoring, and AI-generated review summaries
- Search, tags, projects, recurring tasks, subtasks, reminders, and bulk carry/cancel UI
- A full history browser, undo stack, archive policy, and cross-day editing
- Settings organization: group the current settings surface more deliberately
- Theme marketplace, downloadable themes, per-task themes, and cloud asset sync
- Animated/video/GIF/weather-driven backgrounds and remote background URLs
- Whole-window/content opacity, live desktop capture, per-frame wallpaper sampling, and a wallpaper manager
- Orb progress rings, Todo/weather/count/notification badges, and online avatars or Gravatar
- AI image generation or any other remote image analysis
- Autostart and more elaborate tray behavior
- Sidebar auto-hide, complex snap animations, and other motion polish
- Global shortcuts and click-through
- Fullscreen Desktop overlays with selective click-through regions; current Desktop mode intentionally remains a bounded Widget so wallpaper, icons, and the native desktop context menu stay available outside its HWND
- Multi-monitor hot-plug validation (recorded as a non-blocking deferred Phase 1 lifecycle gate)
- Explorer restart, lock/sleep/resume, fullscreen, and broader Windows-version regression coverage
- Bookmark-manager features on top of Quick Links: favicons, page-title fetching, folders/groups, tags, search, and cloud sync. v1 ships a plain name + URL list only.

The existing `tasks`, `categories`, `shortcuts`, and `app_settings` tables and the Vue/Rust boundaries are the intended foundations. Future phases should add focused repository methods and UI components without moving ordinary presentation/business logic into the Win32 adapter.
